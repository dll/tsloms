# PRD\-TSLOMS\-v1\.0 交通信号灯检测后台运维系统

**项目名称**：交通信号灯检测后台运维系统

**英文名称**：Traffic Signal Light Operation and Maintenance System

**项目简称**：TSLOMS

**文档版本**：V1\.0

**适用场景**：城市交通信号灯设备通信对接、故障自动研判、维修工单流转、运维数据可视化统计

## 一、项目概述

### 1\.1 项目简介

系统对接交通信号灯硬件设备，基于V3版本设备通信协议，实时接收、解析设备上报数据包，自动研判设备故障，触发自动化维修工单下发、流转闭环，同时对故障、工单数据进行聚合统计，通过饼图、柱状图实现可视化展示，解决传统人工巡检滞后、运维数据无数字化统计的痛点，实现信号灯运维智能化、数字化管理。

### 1\.2 核心业务流程

信号灯设备上报数据包 → 后台报文接收解析 → 故障规则研判 → 正常数据入库存档/故障自动生成工单 → 工单派发、处理、闭环 → 数据聚合统计、图表可视化展示

### 1\.3 功能范围

**包含**：设备通信对接、报文解析校验、故障智能判别、维修工单管理、设备台账管理、数据统计可视化、系统权限管理

**不含**：硬件设备改造、运维人员移动端APP（预留对接接口）

## 二、核心功能需求

### 2\.1 设备通信模块

基于信号灯设备V3通信协议，实现多设备并发接入，完成数据包接收、校验、解析，提取设备ID、路口信息、设备状态、故障码、电压电流、时间戳等核心数据；支持心跳检测，自动判定设备在线/离线状态，异常报文日志留存。

### 2\.2 故障研判模块

依托协议故障码\+业务规则，自动识别灯珠损坏、时序异常、电源故障、设备离线等问题；支持故障等级划分、重复故障去重，精准记录故障信息，作为工单生成依据。

### 2\.3 工单运维模块

故障触发后自动生成维修工单，支持工单手动派发、状态更新（待处理/处理中/已完成/已驳回）、维修结果回填、工单闭环；支持多条件筛选、历史工单查询。

### 2\.4 数据可视化模块

**饼图**：故障类型占比、工单状态分布占比统计展示

**柱状图**：日/周/月时段故障数量、各路口故障数量、工单处理效率统计展示

支持时间维度筛选、数据报表导出。

### 2\.5 基础管理模块

设备台账管理、用户角色权限管理、通信参数配置、系统操作日志、报文日志、故障日志查询。

## 三、非功能需求

1\. **性能**：支持百级设备并发接入，报文解析、故障研判毫秒级响应

2\. **可靠性**：关键数据、原始报文日志持久化存储，网络波动不丢失核心数据

3\. **兼容性**：完全适配信号灯V3版本通信协议

4\. **安全性**：后台登录鉴权、接口权限校验、操作日志溯源

## 四、两套落地技术方案（差异化可选）

### 方案一：轻量化快速落地方案（中小型项目、快速上线、低运维成本）

**适用场景**：路口设备数量少、需求迭代慢、预算有限、追求快速交付

**技术栈**

后端：SpringBoot \+ Java（轻量架构，开发高效）

通信：Netty（实现TCP/UDP设备报文接收解析）

数据库：MySQL（业务数据存储）\+ 本地日志文件（报文日志）

前端：Vue2 \+ ElementUI \+ ECharts（快速实现后台页面\+饼图/柱状图可视化）

部署：单机部署 / 宝塔面板部署

**方案优势**：开发周期短、部署简单、运维成本低、适配小体量业务

**方案劣势**：高并发扩展性弱，不支持超大规模设备接入

### 方案二：高可用可扩展方案（大型项目、多路口海量设备、长期迭代）

**适用场景**：城市级多路口设备接入、设备量大、并发高、后续需功能迭代扩容

**技术栈**

后端：SpringCloud Alibaba 微服务架构 \+ Java

通信：Netty（报文解析服务独立微服务拆分）

中间件：Redis（缓存设备在线状态、高频统计数据）\+ RabbitMQ（故障、工单消息异步解耦）

数据库：MySQL（业务主数据）\+ InfluxDB（时序报文、设备状态数据存储）

前端：Vue3 \+ Vite \+ Element Plus \+ ECharts（高性能可视化）

部署：Docker \+ Nginx 集群部署，支持负载均衡

**方案优势**：高并发、高可用、模块解耦，支持海量设备接入、业务横向扩容，适配长期迭代

**方案劣势**：开发、部署、运维成本更高，周期更长

## 五、核心数据模型（精简）
