# TSLOMS 发布审核报告（SAR）v5.0

> 审核日期：2026-08-15  
> 审核依据：`docs/PRD-TSLOMS-v4.3.md`、`docs/SAR-TSLOMS-v4.3.md`、项目开发规范  
> 审核基线：commit `a9ba1c5` + 当前未提交工作区（实时异常流候选增量）  
> 审核方式：需求追踪、代码静态审核、自动化测试、构建检查、依赖漏洞扫描、部署材料审核  
> 发布结论：**不通过（NO-GO），禁止按当前工作区直接发布生产环境**

---

## 一、执行摘要

当前版本具备 v4.3 的主要业务实现，后端单元测试、竞态测试、`go vet`、后端构建、前端类型检查、ESLint 和前端生产构建均可完成；npm 生产依赖审计未发现已知漏洞。

但是，候选版本存在可直接影响权限边界、生产启动、安全基线和验收可信度的阻断问题：

1. 自然语言接口仅要求登录，却能直接创建故障和工单，查看角色可绕过既有 RBAC 写权限。
2. `govulncheck` 检出当前代码路径受 26 个已知漏洞影响，覆盖 Go 标准库、MQTT、JWT、`x/net`、`x/text`。
3. 仓库内生产 systemd 配置不能正确注入密钥，且与生产 Compose 的数据库用户配置不一致；全新部署大概率无法启动，JWT 密钥还可能退化为仓库中可知的字面值。
4. 后端总覆盖率仅 27.2%，前端测试命令不可运行，仓库无 E2E 测试资产，也无本次候选版本的生产 200/E2E 证据。
5. v5.0 实时异常流增量未形成可发布闭环：前端没有可见入口，后端是请求时数据库聚合而非 MQTT 实时分析与自动联动，且存在漏报和统计不一致风险。

因此，本次审核结论为 **拒绝发布**。旧版 SAR 中的生产 E2E 结果对应旧提交，不能替代当前未提交候选版本的验收证据。

## 五、阻断问题（P0）

### P0-01 自然语言接口可绕过 RBAC 执行写操作

**证据：**

- `packages/server/cmd/server/main.go:340` 的 `POST /ai/nl/interact` 未挂载 `RequirePerm`。
- `packages/server/internal/ai/nl.go:407-470` 可直接 `DB.Create` 创建故障。
- `packages/server/internal/ai/nl.go:473-522` 可直接 `DB.Create` 创建工单。
- `packages/server/internal/handler/ai_advance.go:209` 注释声称权限由路由控制，但实际路由没有该控制。

**影响：** 任意已登录用户，包括仅查看角色，可通过自然语言命令创建真实故障和工单；同时可以调用大量 AI 建议接口消耗额度。该行为绕过了普通接口上的 `fault:*`、`workorder:create` 和 `ai:ops` 权限边界。

**整改要求：**

1. 所有 AI 建议、异常流、决策查询至少增加 `ai:ops`。
2. 自然语言写命令在意图识别后再次校验业务权限；创建工单必须校验 `workorder:create`，创建故障应新增或绑定明确的故障创建权限。
3. 最佳方案是拆分只读查询与写命令端点，写端点增加显式确认、幂等键和审计字段。
4. 增加 viewer/operator/admin 的越权集成测试。

### P0-02 Go 运行时和核心依赖存在可达已知漏洞

本机使用 `go1.26.0 windows/amd64` 执行 `govulncheck ./...`，结果为：**代码路径受 26 个漏洞影响**。

重点命中包括：

| 组件 | 当前版本 | 修复版本/要求 | 代表风险 |
|---|---|---|---|
| Go 标准库 | go1.26.0 | 至少 go1.26.6 | `net/http`、TLS、X.509、URL/XML/ASN.1 等多项 DoS、解析和校验问题 |
| `paho.mqtt.golang` | v1.4.3 | v1.5.1 | GO-2025-4173，MQTT 字符串编码问题 |
| `golang-jwt/jwt/v5` | v5.2.1 | v5.2.2 | GO-2025-3553，JWT 头解析过量内存分配 |
| `golang.org/x/net` | v0.21.0 | 按扫描结果升级至已修复版本 | HTTP/2、代理绕过、IDNA 等问题 |
| `golang.org/x/text` | v0.20.0 | v0.39.0 | GO-2026-5970，无效输入导致死循环 |

`go.mod` 只声明 `go 1.22`，Dockerfile 使用可变的 `golang:1.22-alpine`，systemd 部署脚本则依赖目标机现有 Go，均未固定安全补丁版本。

**整改要求：** 升级 Go 工具链和直接/间接依赖，执行 `go mod tidy`，重新运行单测、竞态测试和 `govulncheck`，要求可达漏洞为 0；生产制品需记录 Go 精确版本和依赖清单。

### P0-03 生产 systemd/Compose 配置无法可靠启动且泄露已知密钥语义

**证据：**

- `deploy/systemd/tsloms-server.service:27,32,34,35` 使用 `Environment=KEY=${KEY}`。systemd 的 `Environment=` 不执行 shell 变量展开，会把 `${JWT_SECRET}` 等作为字面值传给程序。
- 若按仓库文件直接启动，JWT 签名密钥将成为公开可知的字符串 `${JWT_SECRET}`，攻击者可伪造令牌。
- systemd 固定 `DB_USER=tsloms`，但 `deploy/docker-compose.prod.yml` 只配置 MySQL root 密码，没有创建 `tsloms` 用户及密码；全新环境连接会失败。
- Redis 未配置密码，生产 Compose 将 MySQL、Redis、MQTT 和 EMQX 管理端口绑定到所有主机接口。

**整改要求：**

1. 使用权限为 `0600` 的 `EnvironmentFile=/etc/tsloms/tsloms.env` 或凭据管理服务，禁止在 unit 文件中伪变量替换。
2. Compose 明确创建应用数据库用户，数据库仅授予所需库权限。
3. 基础设施端口改为 `127.0.0.1:端口:端口` 或内部网络，不对公网暴露；Redis、EMQX 启用认证。
4. 增加 `systemd-analyze verify`、Compose 配置校验和全新环境冒烟测试。

### P0-04 自动化质量门不满足项目规范

实测结果：

- 后端总覆盖率：**27.2%**，低于项目要求的 **80%**。
- 分包覆盖率：AI 32.5%、handler 22.9%、middleware 27.7%、model 57.6%、MQTT 32.7%、service 14.4%、server/config 0%。
- 前端 `npm test` 失败：脚本调用 `vitest run`，但 `package.json` 没有 `vitest` 依赖，`npm ls vitest` 为空。
- 仓库未发现前端单元测试、Playwright/Cypress 配置或 E2E 用例。
- 没有当前候选版本的生产网关/后台 200 和关键用户路径 E2E 证据。

**整改要求：** 修复前端测试工具链；为认证/RBAC、巡检、通知、Copilot、NL 写命令、异常流和部署冒烟补齐测试；覆盖率达到规范后，将测试、构建、漏洞扫描和 E2E 接入 CI，任何失败阻断制品发布。

### P0-05 v5.0 实时异常流候选增量未完成

**前端不可用：**

- `packages/admin/src/views/ai/Workbench.vue:310` 定义 `loadAnomaly`，第 326 行定义 `levelTag`，但模板在第 216 行结束“决策建议中心”标签页，没有异常流标签页、按钮、时间窗选择器或事件表格。
- ESLint 明确报告上述两个函数“定义但未使用”。因此 API 接入代码不会形成用户可操作功能。

**后端不符合“实时流 + 自动联动”定义：**

- `BuildAnomalyStream` 仅在 HTTP 请求时读取数据库快照，没有 MQTT 流处理器、持续检测、主动通知或自动派单。
- PRD v4.3 第 70、136 行对该事项的定义是“MQTT 数据流实时分析，异常即时研判并自动联动派单”，当前实现不满足。
- 该增量没有 v5.0 PRD、专属验收标准、开关、灰度和回滚设计。

**整改要求：** 要么在本次发布中完整移除该未完成增量，要么补齐正式 PRD、前端交互、真实流式处理、联动策略、权限、告警去重、限流、测试和 E2E 后再发布。

## 六、高风险问题（P1）

### P1-01 异常流查询可能漏报并返回不一致统计

- `anomaly.go:63-64` 先对所有报文取 `Limit(maxEvents)`，再过滤异常。若最新报文都是正常签到，更早但仍在时间窗内的告警会被漏掉。
- `anomaly.go:79-81` 的活跃故障没有按 `since` 过滤，用户选择 1 小时也可能看到更早故障。
- `anomaly.go:125-139` 在截断事件前计算 `by_level`，截断后 `total` 取事件长度，可能出现各等级合计大于 `total`。
- 所有 `Find`/`Count` 都忽略数据库错误，数据库异常时可能返回“无异常/运行平稳”的错误结论。
- 新增测试只覆盖报文分类、排序和摘要，没有覆盖数据库聚合、时间窗、limit、错误路径、HTTP 接口和权限。

### P1-02 广播通知的已读状态在用户之间串扰

`user_id=0` 的广播通知只有一条记录和一个 `is_read` 字段。`notification.go:43-53` 允许任意用户直接更新这条共享记录；一个用户标记已读后，其他用户的未读数也会下降。

应增加“通知定义 + 用户通知状态”关联表，或在广播时为每个目标用户生成独立记录。需要至少两个用户的隔离测试。

### P1-03 已停用用户的既有 JWT 在 72 小时内仍可继续使用

登录接口会拒绝 disabled 用户，但 `middleware/auth.go:60` 只验证用户存在，没有检查 `user.Status`。用户被停用后，已签发令牌仍可继续访问接口，直到 72 小时过期。

应在每次鉴权时校验启用状态，或引入令牌版本/撤销列表，并补充停用后立即失效测试。

### P1-04 默认管理员弱口令进入生产初始化路径

`internal/model/db.go:285-302` 在用户表为空时创建 `admin/admin123`。该密码低于项目现有的新用户密码策略，且没有首次登录强制修改机制。

应改为首次启动必须通过安全渠道提供一次性管理员密码，或生成随机临时密码并强制首次修改；生产环境不得包含固定默认凭据。

### P1-05 HTTP 服务缺少超时保护

`cmd/server/main.go:101-104` 创建 `http.Server` 时只设置地址和处理器，没有 `ReadHeaderTimeout`、`ReadTimeout`、`WriteTimeout` 和 `IdleTimeout`。这会放大慢请求和连接耗尽风险。

### P1-06 部署脚本不可重复、无回滚且验证不足

`deploy/scripts/deploy.sh` 直接 `git pull origin main`、在生产机执行 `npm install` 和本地编译，只检查 `systemctl is-active`：

- 没有固定 commit/tag、依赖缓存和制品摘要。
- 没有数据库迁移备份、前后端制品备份和自动回滚。
- 没有 `/health`、登录、网关、后台静态资源和核心 API 冒烟验证。
- `npm install` 不保证严格复现锁文件，应使用 `npm ci` 或 CI 制品部署。

### P1-07 数据库迁移缺少版本化和回滚机制

应用启动时直接执行 GORM `AutoMigrate`，并包含旧表合并后删除操作。仓库没有版本化迁移清单、迁移前备份、回滚脚本和大数据量迁移演练证据。该方式不适合作为可审计的生产发布迁移流程。

## 九、整改优先级与复审条件

### 9.1 第一阶段：关闭安全和权限阻断

1. 修复 NL 写命令和全部 AI 接口权限，补齐角色越权测试。
2. 升级 Go 工具链、JWT、Paho、`x/net`、`x/text`，使 `govulncheck` 可达漏洞归零。
3. 修复 systemd 密钥注入、数据库用户创建、Redis/EMQX 认证和端口暴露。
4. 移除固定管理员默认密码，停用用户令牌立即失效。

### 9.2 第二阶段：完成候选功能和数据正确性

1. 明确实时异常流是否属于 v5.0；补齐 PRD 和验收标准。

### 9.3 第三阶段：补齐发布证据

1. 后端总体覆盖率达到不低于 80%，核心业务路径必须有集成测试。

## 十、审核结语

TSLOMS v4.3 的主体功能已具备可运行基础，后端测试和前后端构建结果说明代码并非不可用；但发布标准关注的是权限边界、安全补丁、部署可重复性和验收证据。当前候选版本在这些方面存在明确阻断，尤其是自然语言越权写入、可达漏洞和无效生产密钥配置，不能以历史生产记录或单纯构建成功代替整改。

**最终审核意见：不通过。完成整改后重新执行全量发布审核，不建议采用带风险上线或边上线边修复。**
