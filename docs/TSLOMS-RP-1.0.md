# TSLOMS AI 化重构计划（RP）v1.0

> 计划日期：2026-08-16
> 计划基线：TSLOMS M1（`v1.0.0`）
> 参考依据：`docs/AI化交通信号灯运维后台系统核心功能清单.md`、`docs/PRD-TSLOMS-v4.3.md`、`docs/SAR-TSLOMS-v6.1.md`
> 目标：在现有可运行的 Go + Vue3 + MQTT + MySQL/Redis 系统上，逐步实现“自动感知、AI 研判、预测维护、自动调度、闭环验收”，保持业务连续性，不进行一次性推倒重来。

---

## 一、重构结论

TSLOMS 当前已经有设备、故障、工单、库存、费用、RBAC、通知、AI 报告、预测、NL 助手和决策中心，适合采用**模块化单体 + 事件驱动内核**的渐进式重构：

- 保留 Gin/GORM、现有 REST 路由和 Vue3 页面，优先替换内部边界；
- 将 MQTT 原始报文、业务故障、AI 判断、调度决策统一成可追踪事件；
- 将 AI 输出从“文本建议”升级为“有证据、有版本、有置信度、有审批状态的业务决策”；
- 所有自动执行都先经过权限、风险分级、幂等、审批、回滚和审计；
- 先完成数据和测试基础，再扩展模型和自动化动作，避免在脏数据上堆叠 AI 功能。

本计划不包含移动端 App/小程序；重点是后台计算、调度、数据治理、接口和配套管理页面。

## 二、现状基线与问题地图

### 2.1 已有能力

| 领域 | 当前资产 |
|---|---|
| 数据采集 | MQTT client/parser/handler、`packet_logs`、签到和离线检测 |
| 故障处理 | 故障记录、状态流转、去重、故障含义、派单关联 |
| 工单闭环 | 建单、派单、状态更新、超时升级、维修费用和库存关联 |
| AI 能力 | 诊断、预测、生命周期、日报、库存/成本分析、Copilot、NL、决策建议 |
| 管理后台 | 设备、路口、用户、部门、RBAC、固件、库存、供应商、采购 |
| 平台治理 | JWT、权限点、操作日志、通知、AI 额度、systemd/Compose/Nginx |
| 前端 | Vue3 + Element Plus + ECharts + Cesium，AI 工作台和异常流页面 |

### 2.2 关键问题

1. 原始 MQTT 报文、故障、预测、通知和工单之间缺少统一事件 ID、因果关系和证据链。
2. 多数 AI 功能仍是请求时调用，缺少模型版本、特征快照、置信度、反馈和效果评估。
3. 故障研判和工单自动化的边界不清晰，自动建单、自动派单和远程处置尚未形成安全状态机。
4. 设备健康度目前以平台级六维评分为主，缺少设备/路口/区域的统一评分口径和时间序列。
5. 数据统计缺少统一指标目录，MTTR、MTBF、故障率、超时率等口径尚未全部固化。
6. 测试、迁移、备份、模型评估和第三方接口契约没有成为发布流水线的硬门禁。

## 三、目标架构

### 3.1 逻辑分层

```text
设备协议/第三方平台
        |
        v
接入适配层 -> 原始报文留存 -> 标准事件层 -> 数据质量/去重
                                      |
                 +--------------------+--------------------+
                 v                    v                    v
           规则研判引擎          AI特征与模型服务       状态/指标计算
                 |                    |                    |
                 +--------------------+--------------------+
                                      v
                              故障案件与决策中心
                                      |
                  +-----------------+-----------------+
                  v                 v                 v
             工单调度          通知/报表          远程指令网关
                  |                 |                 |
                  +-----------------+-----------------+
                                      v
                              修复验证与反馈闭环
```

### 3.2 代码边界

在保持模块化单体的前提下，逐步形成以下内部领域包：

- `internal/ingest`：协议适配、原始报文、标准事件、去重和校验；
- `internal/fault`：故障案件、证据、等级、聚类、根因和状态机；
- `internal/predict`：特征、预测批次、模型版本、风险和养护计划；
- `internal/dispatch`：派单策略、人员负载、距离、审批和执行记录；
- `internal/command`：远程指令白名单、审批、幂等、超时、回滚和回执；
- `internal/asset`：设备生命周期、质保、备件和供应商；
- `internal/metrics`：指标目录、聚合任务、报表和导出；
- `internal/ai`：模型网关、提示词/模型版本、额度、评估和反馈；
- `internal/audit`：不可篡改操作链、风险操作识别和审计查询。

现有 handler 不立即大规模搬迁；先通过 service/use-case 接口隔离数据库访问，再按业务域迁移，降低一次性改动风险。

### 3.3 数据分层

第一阶段不强制引入新数据库，采用 MySQL 分区/归档 + Redis 缓存，验证规模后再评估时序数据库：

| 层 | 建议表/对象 | 保留策略 |
|---|---|---|
| 原始层 | `raw_packets`、原始第三方 payload | 短期热存储 + 对象存储归档 |
| 标准层 | `device_events`、`device_state_snapshots` | 按设备/时间索引，支持回溯 |
| 业务层 | `fault_cases`、`fault_evidences`、`work_orders` | 永久保留，状态可审计 |
| AI 层 | `feature_snapshots`、`model_versions`、`predictions`、`ai_feedback` | 与模型版本绑定 |
| 决策层 | `dispatch_decisions`、`remote_commands`、`command_receipts` | 永久审计，不允许物理删除 |
| 指标层 | `metric_definitions`、`metric_daily_values`、`report_exports` | 可重算、可追溯 |

所有跨层记录必须携带 `event_id`、`device_id/hw_id`、`occurred_at`、`ingested_at`、`source`、`trace_id` 和 `schema_version`。

## 四、按核心功能清单的重构路线

### 4.1 AI 感知采集与数据底座

**目标：** 从“能收 MQTT 报文”升级为“所有设备数据可验证、可回放、可供模型使用”。

**工作项：**

1. 定义 `CanonicalDeviceEvent` 标准事件：设备、路口、协议、事件类型、测量值、质量码、时间、原始引用。
2. 建立 `ProtocolAdapter` 接口，将信号机、灯组、电源、机箱、车检器、视频/卡口适配为独立实现。
3. 增加报文校验、重复键、乱序窗口、时间漂移、非法字段和未知协议的质量问题记录。
4. 将 MQTT handler 改为“快速落原始数据 + 异步标准化”，避免在网络回调中执行重 AI/重 SQL。
5. 实现事件回放工具，用历史原始报文重建故障研判结果。
6. 用分区表和冷热归档支撑至少 12 个月回溯，预留时序数据库适配接口。

**验收指标：** 标准事件字段覆盖率 ≥99%；重复报文识别率 ≥99%；接入到标准事件 p95 ≤2 秒；原始报文可按 `trace_id` 回放。

### 4.2 AI 智能故障研判

**目标：** 从“规则 + 文本建议”升级为可解释的故障案件。

**工作项：**

1. 建立故障案件状态机：`detected -> triaged -> confirmed -> dispatched -> resolved -> verified -> closed`，保留人工驳回和重新打开。
2. 将报文、设备状态、历史故障、天气/时段（可选）、维修记录整理为结构化证据集合。
3. 实现规则初筛、特征模型、LLM 解释三段式编排；LLM 不直接改变故障事实，只生成解释和候选动作。
4. 增加故障风暴抑制、同路口/同批次/同时间窗聚类和主从故障关系。
5. 建立人工确认反馈：误报、漏报、等级修正、根因修正进入 `ai_feedback`，供评估和迭代使用。

**验收指标：** 关键故障类型 precision/recall 有基线；重复告警压缩率可度量；每条故障输出证据、规则/模型版本和置信度；P0/P1 故障必须人工确认后才能进入自动动作。

### 4.3 AI 预测性运维

**目标：** 从“预测页面”升级为可执行的预防性维护计划。

**工作项：**

1. 固化设备运行时长、电压/电流波动、离线、故障频次、维修间隔、环境等特征快照。
2. 为寿命预测和故障预警增加模型注册、训练数据版本、校准曲线、预测时间窗和失效标记。
3. 将预测结果转为“未来 7/30/90 天风险”及预警提前量，不直接等同于真实故障。
4. 根据健康分、质保、区域标准和历史故障自动生成月度/季度养护计划草稿。
5. 建立预测效果评估：提前命中率、误报率、平均提前量、预测覆盖设备数。

### 4.4 自动化运维调度与闭环

**目标：** 从“人工点击派单”升级为受控自动化。

**工作项：**

1. 建立调度候选评分：故障等级、片区、距离、技能、当前负荷、班次和 SLA。
2. 支持 `preview -> approve -> apply -> receipt -> verify` 五阶段，不允许 AI 直接绕过审批写入最终指派。
3. 工单自动生成必须有幂等键 `fault_case_id + action_type`，避免重连/重复报文产生重复工单。
4. 远程指令建立白名单和能力模型：重启、复位、黄闪切换、配时回滚分别配置风险等级、审批人、超时和回滚动作。
5. 工单完成后自动比对修复前后事件、在线状态和故障再现窗口，生成验收结果；失败则进入二次派单。

**开放顺序：** 先自动提醒和草稿，再自动派单；远程控制必须在仿真设备和灰度路口验证通过后逐项开放。

### 4.5 设备健康度评估

**目标：** 统一设备、路口、片区三级健康度。

**工作项：**

1. 将当前六维平台评分拆成可复用维度：工况、故障、通信、老化、养护、资产/备件。
2. 统一 0-100 分、正常/亚健康/故障/老化淘汰四级映射和阈值版本。
3. 保存每日快照和变化原因，支持趋势、排名、下钻到证据。
4. 对评分做人工校准和故障结果回溯，避免“分数漂亮但不预测真实风险”。

### 4.6 资产台账与库存智能化

**工作项：**

1. 设备首次签到/导入自动生成待确认台账，补充型号、安装时间、质保和供应商。
2. 故障、工单、维修、换件、验收事件自动回写设备生命周期。
3. 质保到期、超期服役、批次风险生成提醒并关联采购建议。
4. 以故障类型、设备批次和近 30/90 天领用建立备件需求预测；AI 只生成采购草稿，最终提交仍受采购权限控制。

### 4.7 AI 数据分析与报表

**工作项：**

1. 建立指标目录和口径版本：MTTA、MTTR、MTBF、故障率、闭环率、超时率、重复故障率、预测命中率。
2. 日/周/月/季度报告统一从指标层生成，避免每个页面自行 SQL。
3. 支持 CSV/XLSX/JSON 导出，导出记录写入审计日志。
4. 增加片区和人员运维质量评估，但必须展示样本量、时间窗和置信度，避免简单排名误伤人员。
5. NL 查询只能调用已注册指标工具，禁止由 LLM 拼接任意 SQL。

### 4.8 权限、审计、备份与自监控

**工作项：**

1. 将权限分为查看、研判、派单、采购、远程控制、模型管理、审计导出七类高风险域。
2. 远程指令、自动采纳、权限修改和模型发布必须双重审计，审计记录追加写入并定期归档。
3. 建立 MySQL/Redis/配置/模型/报表的备份清单、RPO/RTO 和恢复演练脚本。
4. 暴露应用指标：MQTT 延迟、解析失败、队列积压、AI 调用/额度、工单 SLA、通知失败、命令回执。
5. 健康检查区分 liveness/readiness；服务启动不能在数据库或 MQTT 不可用时假报 ready。

### 4.9 第三方接口与模型迭代

**工作项：**

1. 协议适配器和上级平台接口统一契约、签名、重试、幂等、限流和错误码。
2. 对外输出设备、故障、健康、工单和报表时提供版本化 API，并记录调用方和数据范围。
3. 建立模型注册表：模型版本、训练数据窗口、特征版本、评估集、批准人、发布状态、回滚版本。
4. LLM 提示词、规则版本和输出 schema 纳入 Git/数据库版本管理，保留输入摘要和脱敏反馈。

## 五、分阶段实施计划

### P0：基线和质量门（第 1-2 周）

**目标：** 让每次重构可验证、可回滚。

- 清理并锁定发布分支、Go/Node 精确版本和依赖清单；
- 将 `go test`、race、vet、gofmt、govulncheck、前端 test/lint/build、smoke 接入 CI；
- 把总覆盖率从 28.5% 起步提升到 50%，先覆盖 handler/service/mqtt 安全路径；
- 完善迁移版本、备份和回滚脚本；
- 建立测试数据工厂、可控时钟、MQTT 报文 fixture 和预发布环境。

**出口门：** CI 全绿、工作区可重建、覆盖率趋势可见、回滚演练成功。

### P1：事件与数据底座（第 3-5 周）

- 标准事件 schema、协议适配器接口、原始报文归档、去重和质量问题表；
- `ingest -> normalize -> persist` 异步链路，增加 trace_id 和回放工具；
- 设备状态快照和按时间/设备索引；
- 现有 MQTT handler 迁移为适配器调用，不改变现有业务 API。

**出口门：** 事件字段覆盖率 ≥99%、回放结果一致、处理 p95 ≤2 秒、旧接口回归通过。

### P2：故障智能研判与预测（第 6-9 周）

- 故障案件状态机、证据集合、聚类/风暴抑制；
- 规则 + 特征模型 + LLM 解释编排；
- 预测模型注册、特征快照、风险时间窗和反馈；
- 健康评分设备/路口/区域三级下钻；
- 离线评估集和人工反馈闭环。

**出口门：** 关键故障 precision/recall 达到基线；每条预测可追溯；无证据的 LLM 结论不可进入自动动作。

### P3：自动调度与闭环验收（第 10-13 周）

- 自动建单幂等、调度候选评分、预览/审批/执行状态机；
- 工单完成后的设备数据校验和二次派单；
- 远程指令网关、白名单、审批、回执和回滚；
- 先在仿真设备和低风险动作上灰度。

**出口门：** 自动派单成功率、重复工单率、SLA、修复验证准确率可度量；高风险命令全部有审批和回滚记录。

### P4：资产、指标与智能经营（第 14-16 周）

- 生命周期/质保/备件自动回写；
- 指标目录、MTTR/MTBF、报表导出和片区质量评估；
- 备件需求预测与采购草稿；
- 运营健康趋势和决策中心升级。

**出口门：** 指标口径统一、报表可重算、采购建议可解释、资产关键字段自动维护率 ≥90%。

### P5：平台化与持续学习（第 17-20 周）

- 第三方平台双向同步、版本化 API、模型注册和灰度；
- 数据/模型/配置备份恢复演练；
- 审计异常识别、自监控、容量和压测；
- 覆盖率达到 80%，形成正式全量发布门禁。

## 六、关键接口与状态设计

### 6.1 推荐新增接口

| 接口 | 用途 | 权限/约束 |
|---|---|---|
| `POST /api/v1/events/ingest` | 内部标准事件写入 | 仅内部服务签名，幂等 `event_id` |
| `GET /api/v1/events/:id` | 事件和原始证据回溯 | `audit:read` 或 `ai:ops` |
| `POST /api/v1/ai/diagnosis/run` | 对故障案件执行研判 | `ai:ops`，保存模型/规则版本 |
| `GET /api/v1/ai/health/devices` | 设备/路口/区域健康度 | `ai:ops` |
| `POST /api/v1/dispatch/preview` | 生成派单候选 | `dispatch:manage`，只读预览 |
| `POST /api/v1/dispatch/:id/apply` | 采纳派单决策 | `dispatch:manage` + 审计/幂等 |
| `POST /api/v1/commands/preview` | 远程指令风险预览 | `command:preview` |
| `POST /api/v1/commands/:id/approve` | 审批高风险指令 | `command:approve`，双人/分级审批 |
| `GET /api/v1/metrics/catalog` | 指标目录和口径 | `report:read` |
| `POST /api/v1/models/:id/publish` | 模型版本发布 | `model:manage` + 审批 |

### 6.2 状态机约束

- 故障状态只能由领域 service 转换，handler 不直接写任意状态；
- 自动派单、远程指令、模型发布必须支持 `pending/approved/executing/succeeded/failed/rolled_back`；
- 每次状态转换记录操作者、来源（人工/规则/模型）、版本、原因、trace_id；
- 重试必须使用幂等键，失败重试不得产生重复工单、重复采购或重复指令。

## 七、AI 治理与安全红线

1. LLM 不直接执行 SQL、MQTT 或数据库写操作，只能选择注册工具并提交结构化参数。
2. AI 输出必须包含 `source`、`model_version/rule_version`、`confidence`、`evidence_ids` 和 `expires_at`。
3. P0/P1 交通安全相关动作默认人工确认；自动化只从提醒、草稿、低风险可回滚动作开始。
4. 所有模型、提示词、规则和指标均版本化；生产发布支持回滚到上一版本。
5. 输入到外部 LLM 前脱敏设备敏感信息、人员联系方式和内部凭据；记录 token/额度和失败原因。
6. AI 反馈必须区分“事实修正、等级修正、动作采纳、动作拒绝”，不能只记录一句自然语言评价。
7. 对 AI 自动决策设定每日额度、速率限制、异常熔断和人工总开关。

## 八、测试与验收策略

| 层级 | 必须覆盖 |
|---|---|
| 单元测试 | 协议解析、去重、故障分级、评分、SLA、权限、幂等、提示词 schema |
| 集成测试 | MQTT/数据库/Redis、巡检协程、通知隔离、故障到工单、库存到采购 |
| 契约测试 | 第三方协议、上级平台 API、模型输入输出 schema、错误码和重试 |
| 回放测试 | 固定历史报文集重放，验证事件、故障、预测和工单结果可复现 |
| 性能测试 | 接入吞吐、事件延迟、异常流查询、NL 限流、报表大数据量 |
| E2E | 登录/RBAC、巡检通知、Copilot、NL 查询/写命令权限、决策采纳、异常流、回滚 |
| 安全测试 | JWT、停用账号、越权、命令审批、敏感日志、依赖漏洞、备份权限 |

质量目标：后端总覆盖率 ≥80%；核心域（ingest/fault/dispatch/command/audit）≥90%；关键 E2E 100% 通过；P0/P1 安全漏洞为 0；关键接口 p95 与事件延迟满足阶段指标。

## 十一、成功标准

完成 RP-1.0 后，TSLOMS 应能够：

- 自动接入并标准化多类设备事件，异常可回放；
- 对故障给出有证据、可解释、可评估的研判和预测；
- 在权限、审批、幂等和回滚约束下自动生成/派发/验收工单；
- 统一计算设备、路口、区域健康度以及 MTTR/MTBF 等指标；
- 自动维护资产、质保、备件和报告数据；
- 对每个 AI 决策回答“基于什么数据、哪个版本、谁批准、执行结果如何”；
- 在测试、漏洞、备份、监控和回滚证据完整的前提下持续发布。

**原则：先把数据、状态、权限和证据链做成可靠系统，再逐步提高 AI 的自动化权限。**
